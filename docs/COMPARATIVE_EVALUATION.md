# Comparative engineering evaluation
## What counts as improvement
Same feature does not mean same implementation. Identify common job, interfaces and observable acceptance obligations. A novel architecture may give equivalent behavior with fewer dependencies, lower latency, lower cost or better reliability. Conversely a simpler approach can fail on retries, concurrency, privacy or scale. Compare the alternatives on an explicitly defined context, never infer original proprietary backend.
Examples (hypothetical, not measured): compare polling vs webhook for allowed event sync, or one browser driver+REA observer vs repeated manual capture for an owned fixture. Keep both if conditions differ. An unsuccessful attempt may teach a better preflight or fallback. A confirmed duplicate adds provenance, not a new capability.
## Protocol
- Freeze baseline approach/version, target/task fixture, environment, scope, permissions, acceptance obligations, hardware, model/tool versions, budget and time window before trial. Record context_id and fixture_id/hash. Use same inputs and equivalent resources; avoid repeated sampling from target beyond authorization. Use separate training/dev and held-out fixtures; no peeking or tuning on holdout. Reset state, control warm/cold runs, capture repeated trials and variation when relevant.
- Hard gates: functionality, security/privacy, authorization, license and critical fidelity. Any failure prevents recommendation for that context. Compare performance only after gates pass. For implementation track p50/p95 latency, cost, memory, reliability, complexity, integration coverage, maintainability as relevant. For investigation track verified obligations/total, time/cost to evidence, false claims caught, repeated steps, unresolved gaps, tool failure/recovery, manual effort. Blocked/untested obligations remain in denominator; no fake efficiency by dropping requirements.
- Choose metrics, direction (min/max), units, tolerance, sample count and aggregation before tests. Record raw artifacts, uncertainty and known confounders. Compare measured baseline and challenger using same context, same metrics and gates. If one wins some and loses others, report tradeoff; if evidence mismatched report incomparable. Only recommend for scoped context, explain reversal conditions. A small numerical improvement may be noise; require meaningful tolerance/repeated evidence. No universal numeric score.
- Independently reproduce important results; record reviewer, test receipt and independent context. Report measurement drift (new version, platform, plan, different targets). Revalidate when relevant dependencies change.
## Workbench-level learning experiment
Freeze a no-prior-knowledge baseline and a prior-knowledge-assisted strategy for representative owned tasks. Allocate equal budget and scope, compare on held-out tasks not used to develop cards, include failed cases and uncertainty, track human corrections and evidence quality. Repeat on diverse categories; use blinded review when possible. Record in knowledge/evaluations/ with raw-safe receipts, date, version, methodology, result and limits. If results regress, revert default changes and preserve failures. No improvement claimed until results exist.

The CLI checks same context/fixture, gates, metric set/units/directions/tolerance and computes DOMINATES, BASELINE_DOMINATES, TRADEOFF, TIE or INCOMPARABLE. It does not establish fairness, statistical significance or truth. Actual evidence and separate reviewer still required.

## External challenger and ground-truth leads
Read lea­nrea (aicodeking/leanrea), rea-lab (pablodiazjorge/rea-lab) and rea-groundtruth (UnknownHacker1/rea-groundtruth) as described in RESOURCE_AUDIT.md. Their reported benchmarks and failure cases are version/platform-specific, not local proof. Use authorized source-known or synthetic fixtures; compare no specialist tool/direct CLI, leanrea, REA, Craft Anything and relevant combinations on the same obligations. Evaluate false negatives (including empty analyzer output), not just correct positive findings. Preserve cost and evidence tradeoffs. Do not generalize or change defaults until independently verified.
