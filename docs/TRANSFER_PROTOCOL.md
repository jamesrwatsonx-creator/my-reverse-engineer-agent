# Two-repository handoff and feedback
Research repository is authoritative for original interview, evidence, observed functionality, alternative architectures, learning and provenance. Production repository is authoritative for design choices, actual implementation, tests, releases and operations. Same ChatGPT conversation can coordinate; recover state from Git after a context reset. No product implementation in investigation except approved minimal fixtures.
## Prepare a new destination
1. Finish research handoff or explicitly mark partial/blocked. Review scope, open obligations, decisions, dependencies (upstream exact pin, license, required runtime/config, test status, alternatives), design vs behavior requirements and build permissions. Confirm destination owner/repo and branch. Do not create/modify unrelated repos or assume build authorization.
2. Commit the reviewed research content first. Create target handoff/ with PRODUCT_SPEC.md, ARCHITECTURE.md, UX_SPEC.md, CONTRACTS.md, DEPENDENCIES.json, ACCEPTANCE.md, BUILD_PLAN.md, GAPS.md and BUILD_AGENT.md. These are self-contained selected specs and explicit uncertainties, not raw target evidence dumps. Build agent reads these and destination AGENTS/CLAUDE first. Include source evidence IDs and references to immutable research commit. Dependency file includes source URL, exact revision, license review, supported environment, setup docs, fixture result, credentials *names* only, fallback; unresolved ones explicitly blocked. Do not claim all dependencies work without receipts.
3. Generate handoff/MANIFEST.json with source repo, source research commit (before package), target slug, destination, readiness PARTIAL or BUILD_READY, package version, list of permitted relative paths and SHA256 bytes hashes, owner approval reference. No secrets/private target data, unauthorized assets, raw auth traces or machine-specific executables. Independently review package; structural verify command checks file list and hashes only. For later immutable package link, use commit containing the manifest, stored outside manifest to avoid circular hash. Keep older package commits and transfer history.
4. Commit package, verify files and hashes, copy reviewed allowlisted files into destination docs/reconstruction/ (not the whole research repo). Add destination AGENTS.md, CLAUDE.md or existing compatible instructions referencing package, build gates, root README, decision log and PROJECT_STATE.md. Store original research repo/slug, package commit, hash manifest, accepted scope and destination commit in both repos' transfer receipts (destination may reference source; source records destination receipt afterward). Verify copied bytes and destination commit before claiming transfer. Do not overwrite existing destination code or policy; review merge conflicts and authorization.
5. Build independently in destination with Cursor, v0, Claude, Codex or other tools. Resolve design, integration and deployment decisions using actual requirements. Verify tests and deployment. If a dependency is blocked, select approved alternative and log ADR; no silent fidelity change.
## Update protocol (not automatic mirroring)
Research changes: create new package/version and diff, list superseded assumptions, effects on destination and re-test needs. Destination reviews/accepts or rejects; preserve local decisions. Production changes: record new implementation pattern, version, benchmark evidence, failure, compatibility, and actual code/test references. Send sanitized feedback into target FEEDBACK.md and LEARNING_DELTA.json; compare with prior variants, independent review before global promotion. Research/production commit refs, date, actor, approval, changes, tests and pending items in TRANSFERS.md. Never overwrite canonical observations with independently built behavior. No credentials, proprietary target data or unintended source redistribution.
## Readiness
PARTIAL means handoff can support planning but gaps remain; BUILD_READY requires reviewed critical obligations, working selected dependencies or explicitly approved replacement plans, and owner acceptance of known risks. PRODUCTION_READY determined only by actual destination implementation and tests. Package integrity is not completeness or runtime verification.

GAPS.md must summarize GAP_REGISTER.json and gap audit, original knowledge limits, independently tested alternatives, unresolved obligations and proposed fixtures. ACCEPTANCE.md carries scoped fidelity axes, explicit tests/tolerances, actual receipts and production-readiness gaps. Do not add unverified provider executables as installed dependencies.
