# First-stage upstream review (every investigation)
1. Access original [REA repository](https://github.com/morluto/rea), [releases](https://github.com/morluto/rea/releases), [commits](https://github.com/morluto/rea/commits/main/), [official documentation](https://rea.tools/) and npm registry (rea-agents). Record time UTC, immutable main commit and published release, npm dist-tag if verified, user fork head, previous review and installed version (NOT_RUN if not available).
2. Compare changes since prior review using release notes, git compare/diff, changed source/docs/tests, provider and MCP/CLI contracts, supported targets, evidence/coverage and output limits, migration notes, deprecations, bug fixes, security/permissions and host requirements. Page relevant changes; if history too large, state range and unreviewed remainder. Focus on target relevance and reusable improvements; do not claim exhaustiveness.
3. For each important change: source URL/commit, what changed, which target types or prior gap it affects, expected benefit (hypothesis), compatibility/risk, proposed fixture, adopt/test/defer/no impact and reason. Separate upstream main from released package and actual runtime. Retain old pin/evidence; stable pin preferred unless reviewed source build is justified and tested. No automatic installs, config mutations or upgrades.
4. Recheck at Claude/Codex execution before invoking REA: installed version, doctor, providers, actual live MCP catalog, harmless fixtures and adapter compatibility. If upstream unavailable or no installed tool, record BLOCKED and use permitted last verified fallback or defer relevant lane. Do not pretend fresh or complete. If new upstream changes are breaking, validate evidence consumers and preserve schema-version provenance.
5. Review [Replit documentation](https://docs.replit.com/) and [changelog](https://replit.com/changelog) and assess platform suitability per REPLIT.md. Document relevant new capabilities, dependencies, limitations, costs, portability and test proposals. No account connection or paid deployment without approval.
6. Append dated entries in target UPSTREAM_REVIEW.md (initial preparation plus execution rechecks). Before a target exists, use review session notes and copy relevant receipt into case on creation. Update central registry/resources only for actual discoveries; use LEARNING_DELTA and independent review for improvements. No forced novelty, no global default changes without regression.
## Receipt fields
review UTC, reviewer/session, target slug, previous receipt/commit, official main SHA, release tag/date, npm version/status, fork SHA, installed status/version, sources read, range reviewed/limitations, changes with impact/test/disposition, Replit findings/relevance, fallback/blockers, link to learning items and next check.
