# Developmental engineering intelligence
The repository learns at two levels: (1) capability knowledge (how to build or integrate a feature), (2) investigation knowledge (how to obtain stronger evidence, select tools, reduce uncertainty and avoid repeated failures). A third layer retains composition knowledge: how individually useful pieces interact, including incompatible versions, failure propagation, permission boundaries and efficient execution sequences. Never confuse target observation with verified alternative or production proof.

## Foundations and limitations
Case-based reasoning uses retrieval, reuse, revision and retention; see [Aamodt & Plaza, 1994](https://journals.sagepub.com/doi/abs/10.3233/AIC-1994-7104). Architecture decision records retain context, choice and consequences; see [GDS guidance](https://gds-way.digital.cabinet-office.gov.uk/standards/architecture-decisions.html). Held-out evaluation and test contamination controls are motivated by [NIST AITE](https://pages.nist.gov/ai-technology-evaluation/). These are design precedents, not proof this specific repository has improved. Its benefit must be measured prospectively.

## Knowledge model
- Target-specific case: canonical folder contains literal goals, feature IDs, evidence, architecture hypotheses, findings, failed attempts, alternatives and actual test receipts.
- Canonical capability: stable ID named by job and interface, not vendor; e.g. calendar-conflict-resolution, webhook-delivery. Record aliases and distinct meanings; do not merge merely because names match.
- Variant: distinct implementation or investigation method, version, conditions, dependencies, input/output, costs, failure modes, security, license, evidence. Multiple variants can coexist.
- Composition: ordered tool/architecture chain, explicit interface compatibility and end-to-end receipt; individual component passes do not prove composition.
- Negative knowledge: scoped failures, inaccessible surfaces, false hypotheses, incompatibilities, wasted effort, reversal conditions. Never equate blocked with impossible universally.
- Knowledge index: knowledge/index.json records reviewed variants and dispositions with source target, evidence refs and revision. Detailed capability cards go under knowledge/capabilities; methods under knowledge/methods, composition under knowledge/compositions, negative findings under knowledge/negative. Store portable sanitized descriptions only. Target-specific data stays in source case. Graph edges IMPLEMENTS, ALTERNATIVE_TO, COMPLEMENTS, DEPENDS_ON, INCOMPATIBLE_WITH, FORK_OF, REQUIRES_AUTH, REQUIRES_PAYMENT, HOSTED_ONLY, LOCAL_FIRST, SUPERSEDES_IN_CONTEXT, CONTRADICTS. Preserve source lineage, version/time and counterevidence.

## Per-target learning loop (required even if blocked)
1. Baseline before work: record revision, known cases, retrieved cards, selected tools and why, planned fixtures and metrics. Search prior capabilities by job/alias/interface, not product name. Read actual cases; do not equate keyword score with relevance. Revalidate stale pins and scope.
2. During work: record REUSE_LOG entries (prior ID/version, adaptation, outcome and evidence), failed approaches, new evidence and hypotheses. Keep raw results in case. Repeat lookup when a new feature is discovered.
3. Extract LEARNING_DELTA.json items at checkpoints and closeout. Classify NEW, CORROBORATION, VARIANT, COMPOSITION, METHOD, FAILURE, CONTRADICTION, RETRACTION or NO_CHANGE. Attach source refs, actual fixture receipts, limitations, context and known comparable cards. If nothing portable, explicitly record why instead of inventing novelty.
4. Normalize: same user outcome may have different mechanism, constraints or architecture. Compare against each existing applicable variant. Duplicate claims link additional evidence; don't duplicate cards or count non-independent sources as corroboration. Different efficiency or security tradeoff becomes a contextual variant. No global winner from one feature or app.
5. Evaluate: use docs/COMPARATIVE_EVALUATION.md. Freeze baseline and fixtures, measure alternatives under same constraints; retain held-out cases and failures. Do not promote a candidate simply because it looks better, or because output came from Claude/Codex. Incomparable results stay incomparable. Source review is not runtime proof.
6. Independent review: candidate → validated-in-context, rejected, needs-retest, or deprecated. Reviewer must not be the proposing agent; separate run/owner records approval and actual evidence. A failed method can be valuable as a validated negative result, not a recommended method. Index changes explicit and audited; no silent changes to global default or policy. Preserve historical decisions; a retraction supersedes rather than erases. Structural CLI checks are not independent verification.
7. Retrieve and adapt next time: use only validated-in-context cards as supported suggestions; show alternatives and relevant caveats. Unvalidated findings are research leads. Log reuse result; new contradictions reopen prior findings. Stale tools/providers trigger revalidation. Keep context small, retrieve relevant evidence on demand.
8. Closeout: target STATUS records learning disposition, reusable IDs, unresolved candidates and next tests. Run audit; review may be pending without blocking research handoff if clearly stated, but never label an unreviewed card validated. Export reviewed implementation patterns with provenance to Maliky Repository Intelligence only when requested.

## Governance and measurement
Default routing or general policy changes are separate reviewed proposals with regression tests, protected holdouts and rollback commit. Require evidence across more than one materially distinct context before broad generalization (not a magic count; explain independence and limits). Preserve variants on Pareto frontier, favor hard constraints and owner goals. Measure effectiveness of the whole workbench, not accumulated notes; use comparative evaluation. No automatic model training, autonomous background execution, or guaranteed improvement per case.
