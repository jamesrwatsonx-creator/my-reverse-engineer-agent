# Universal Gap Closure Engine
## Objective
Reduce uncertainty and independently satisfy observable owner-approved requirements. An original mechanism can be non-identifiable even when a replacement meets every tested obligation. Preserve both outcomes.
## Execution (mandatory for every target)
1. Initialize current universal contract, catalog/upstream freshness, Replit assessment and prior knowledge. Examine permitted public/authorized target, classify mixed target types and ask only missing essential questions. Establish feature IDs, actors, acceptance obligations, target version, access and budget. No unapproved target interactions.
2. For each scoped obligation record whether observed, documented, inferred, unknown or blocked. Classify uncertainties in GAP_REGISTER.json with unique gap ID, obligation ID, feature ID, route_id from registry/gap_routes.json, priority, limitation type, allowed scope, evidence references, hypotheses, intended test and acceptance tolerance. A single feature can have multiple gap routes. Mark out-of-scope with owner rationale, not silent deletion. Create new route only after review; use closest existing route meanwhile.
3. Run gap_engine.py plan --slug <target>. It maps explicit route IDs to method, prerequisites, candidates, boundaries and acceptance; does not discover target features or select a verified provider automatically. Filter candidate tools by actual target/host, input availability, licensing, permission, cost and evidence gain. Reuse prior validated cards, check latest source and pins. Record chosen tools, rejected alternatives, fallback and smoke fixture. Do not install all candidates.
4. Triangulate independent documentation, allowed observations and authorized artifacts. Distinguish correlated sources. Generate at least two plausible hypotheses where useful; specify prediction, discriminating observation, uncertainty and expected information gain. If no legal discriminating evidence exists, do not probe; switch to independent outcome reconstruction. Model state/constraints, contracts, events, formats and data on permitted evidence or independent fixtures. Test on owned/explicitly approved environments, keep test and holdout data separate. No extraction of secrets or hidden proprietary implementation; no load or active test without authorization.
5. For each attempt record UTC, source version, scenario and evidence IDs, tool/version, fixture hash, input/output artifacts, result, cost and residual gap. A model result or likely invariant is a hypothesis until independently supported. Compare alternative implementations on equivalent conditions, hard gates first, use docs/COMPARATIVE_EVALUATION.md. For concurrency, model bounds and assumptions; a passing model is not proof of implementation. For opaque AI algorithms use independent task benchmarks, not model extraction. 
6. Update knowledge_status and functional_status separately. A VERIFIED_ALTERNATIVE can close a scoped functional gap while knowledge_status remains UNKNOWN/BLOCKED. Distinguish EXACT_DOCUMENTED/OBSERVED from inferred; never assert hidden mechanism. Stop when acceptance passes, further permissible evidence has insufficient marginal value, limitation is non-identifiable, access prohibited, or budget exhausted. Keep residual unknowns and next action. No forced closure.
7. At handoff audit structural completeness, compare each scoped requirement and record all unresolved items, per-axis pass/fail/blocked/not-run denominator, and separate production readiness. Transfer gap report and independent test plans to production repository; receive implementation feedback. Promote reusable knowledge only through existing independent review, protected regressions and LEARNING_DELTA.
## Gap register
JSON: {schema_version:1,target_slug:"...",assessment:"PENDING"|"ASSESSED"|"NO_GAPS",no_gaps_reason:null,items:[{id:"gap-1",feature_id:"feature-1",obligation_id:"obligation-1",route_id:"business-logic",priority:"critical"|"high"|"normal",limitation:"missing-evidence"|"tool-coverage"|"restricted"|"non-identifiable"|"budget"|"unavailable-data",allowed_scope:"...",knowledge_status:"DOCUMENTED"|"OBSERVED"|"INFERRED"|"UNKNOWN"|"BLOCKED",functional_status:"NOT_RUN"|"PASS"|"FAIL"|"BLOCKED"|"DEFERRED",evidence:[],hypotheses:[],attempts:[],acceptance:"...",residual:"...",disposition:"OPEN"|"TEST"|"RESOLVED"|"BLOCKED"|"DEFERRED",reason:"..."}]}. Evidence and attempt records should cite actual artifact refs/hash, version, scenario, outcome and limits. Functional PASS requires actual pass receipt and evidence; use blocked/deferred with reason if missing. RESOLVED requires a linked persisted verification receipt (byte_match, oracle_harness, behavioral_equivalence) with functional PASS, or an explicit YELLOW assessment with named residual_uncertainty and linked evidence. Documented/observed knowledge alone is not closure. YELLOW remains unresolved for full equivalence. No claiming functional PASS without test. NO_GAPS requires explicit scope and rationale, not empty scaffold. Audit checks record structure and status consistency, not actual truth, identity or completeness of feature discovery. 
## Runtime boundaries
No external provider is executed by the local engine. Follow GAP_TOOL_RECIPES.md for proposed adapter workflows and verify actual installed signatures and interoperability. Each real target needs selected-provider receipts.

The current implementation creates GAP_REGISTER.json for new targets. Existing cases must add it manually on next review without overwriting prior evidence. For `attempts`, each PASS assertion needs a nonempty `receipt` reference. Audit checks structure and, for RESOLVED, looks up persisted verification evidence with --evidence-store PATH; this does not rerun a verification harness. Invalid legacy RESOLVED reports effective OPEN with retained knowledge and reason; source register is not silently rewritten. For critical OPEN/TEST gaps, explicitly record a justified BLOCKED/DEFERRED disposition or resolve them before handoff. Report unresolved items even if audit is structurally valid.

## Advanced routes and fallback policy
See ADVANCED_ANALYSIS.md and registry/gap_routes.json. The planner emits fallback_policy.steps based on limitation: restricted stops the lane; non-identifiable/unavailable-data records unknown and uses an independent model; budget recovers retained evidence and narrows scope before considering alternate providers; other gaps require scope/fixture verification before alternate methods. provider_execution_allowed is always false because this is planning only. Follow explicit permission/host gates before separately approved execution. The catalog has 33 routes; earlier counts are historical.
